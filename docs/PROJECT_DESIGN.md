## 3. 目标架构

### 3.1 保持模块化单体，不重写全部项目

```text
浏览器
  │ HTTPS（唯一业务公网入口）
Web 入口 / Vue 静态文件
  │ /api
Spring Boot 模块化单体 ─── MySQL（业务事实、审核、幂等凭据）
  │
  ├── Redis（登录令牌、短期缓存、热度；不是采集结果唯一存储）
  │
  └── 内部采集 API ← Python 单任务采集器
                         ├── 来源发现、抽取、分类、摘要
                         └── 独立持久 outbox（待交付结果）

服务器外：加密备份；后续按需要启用对象存储
```

**低量采集交付默认选择：HTTP + 持久 outbox + MySQL 幂等事务。** 当前来源少、低频、处理串行，不增加 Kafka/RabbitMQ，不为简历指标保留复杂消息链。Redis Streams 可以作为未来扩容备选，但首期不并行维护两种采集交付路径。

选择理由：明确“服务端事务提交成功”这一完成点；Redis 不可用时不能让已处理结果消失；减少列表队列、手动消费、定时消费之间重复逻辑。HTTP 本身不保证可靠交付，可靠性由第 6 节的持久化、重放与服务端幂等共同实现。

### 3.2 代码职责边界（渐进迁移）

| 模块 | 负责 | 不负责 |
|---|---|---|
| identity | 登录、角色、服务身份 | 自动决定文章发布 |
| content | 文章、游戏、内容类型、公开查询 | 抓网页 |
| moderation | 审核、上下架、操作审计 | 信任前端传入的管理员角色 |
| ingestion | 来源、内部交付、幂等、采集记录与运行摘要 | LLM 网页正文生成 |
| interaction | 点赞、收藏、评论、浏览、热度 | 暴露草稿或其他不可见内容 |
| operations | 容量状态、健康、发布开关 | 在 Web 请求中执行 shell |
| Python adapters | 列表/API/RSS 发现和站点抽取 | 写业务 MySQL |
| Python pipeline | 标准化、判定、摘要、重试、outbox | 决定数据库主键或管理员身份 |

建议 Java 最终按业务模块组织，每模块内部 controller/service/repository/dto；Python 按 adapters/extraction/classification/delivery/runtime 拆分。**禁止一次性搬动所有包或重命名全部类。** 修改到哪个业务切片，再收敛对应代码与测试。

DTO 与数据库实体分离。公开接口不直接序列化 Article 数据库实体，也不返回完整抓取记录、审核备注、内部错误栈和服务令牌。

## 4. 产品与内容模型

### 4.1 游戏和内容类型分离

游戏稳定代码：`delta-force`、`valorant`、`cs2`、`apex-legends`。数据库数字 ID 只是内部键，禁止 Python 和前端写死 `5/8/9/10` 作为跨环境契约。

别名表示实体线索而非准入证明，例如 CS2/Counter-Strike 2/反恐精英2、VALORANT/无畏契约。单独 CS、三角洲等歧义词不能直接通过。CS:GO 历史资料和与 CS2 无直接关系的系列内容不自动等价为 CS2；存疑待审核。

文章类型代码：`announcement`、`patch_notes`、`event`、`new_content`、`guide`、`esports`。每篇一个主类型，可关联多个白名单游戏，避免重复存同一篇跨游戏新闻。前端筛选按 article-game 关联完成。

### 4.2 三类内容决策

- **ACCEPT**：主体属于白名单游戏，类型允许，来源与结构可信，必需字段齐全，无广告/无关内容/重复问题，且当前规则版本已通过评测。
- **REVIEW**：游戏归属歧义、多游戏混杂、类型不明、证据不足、未验证来源、输出结构异常、关键元数据冲突或近重复。
- **REJECT**：明确非白名单主体、明确禁入内容、无有效正文、确认重复等。记录机器可读原因码。

例：`GAME_NOT_ALLOWED`、`INCIDENTAL_MENTION`、`DISALLOWED_TYPE`、`LOW_EVIDENCE`、`INVALID_PAYLOAD`、`EXACT_DUPLICATE`、`NEAR_DUPLICATE`、`SOURCE_UNVERIFIED`。

官方来源不免校验：官网也可能有跨游戏营销或页面抽取失败。官方身份只能由来源配置确定，不能让页面内容或 LLM 自报。

模型输出 confidence 只供辅助诊断，不能解释为真实准确率。自动发布阈值由标注样本确定；未达评测门槛的来源使用 REVIEW 模式，不通过放宽阈值追求数量。

### 4.3 阅读与发布状态

- `readingMode = FULL_TEXT`：默认模式。采集入库的正文（服务端确定性清洗后）随文章一起存储，公开详情接口按 id 读取并作为纯文本返回，前端以文本渲染，不做 HTML 注入。标题、来源、原始语言、原文时间（未知则明确标注）、站内发布时间及原文入口同时展示；原文入口始终保留作为出处标注。
- `readingMode = EXTERNAL_SUMMARY`：保留给明确不允许站内展示正文的来源。该模式下详情接口的 `content` 为 `null`，只返回摘要与原文入口，不伪造站内正文。
- 入库正文写入 `article.content`（`MEDIUMTEXT`），同时以内容哈希副本写入 `article_content.sanitized_html` 供审计；公开读取只走 `ArticleMapper.selectPublishedContentById`，显式投影标题、正文与展示元数据。
- `status = DRAFT / PENDING_REVIEW / PUBLISHED / REJECTED / UNPUBLISHED`。
- 发布必须通过 Java 的统一发布服务；管理员修改或机器重放均不能绕过状态、角色与容量检查。
- 已发布文章的抓取更新先创建候选修订；首期不静默覆盖线上内容，管理员确认后替换。不是同 URL 一变更就发布新文章。

`PUBLISHED` 之外的文章不能出现在公开列表、详情、搜索、热榜、轮播、收藏展示或互动目标中。详情未发布/不存在统一 404，避免泄露审核内容；管理员使用单独管理接口。

### 4.4 数据表设计方向

由迁移任务确定最终 SQL/长度/索引，本表是必须表达的业务语义，不是已存在的表。

| 表/实体 | 主要字段与约束 |
|---|---|
| game | id、code 唯一、中文/原文名称、aliases、enabled；只有四个初始启用项 |
| source | code 唯一、官方/媒体类型、允许域名、游戏范围、语言、适配器、周期、自动发布开关、验证时间/状态 |
| article | id、title、summary、source_id 可空（管理员原创）、original_url、canonical_url_hash、original_title、source_language、original_published_at 可空、ingested_at、published_at、updated_at、content_type、reading_mode、status、created_by、revision |
| article_game | article_id + game_id 联合唯一；支持跨游戏去重后多标签 |
| article_content | article_id、sanitized_html 可空、content_hash、extractor_version；正文与列表 DTO 分离 |
| ingest_receipt | event_id 唯一、payload_hash、article_id 可空、最终决策、rule_version、created_at；幂等返回凭据 |
| ingest_record | 来源候选、规范 URL hash、内容 hash、阶段、拒绝/审核原因、版本、最后错误摘要、重试/运行关联；不无限保存原始网页 |
| ingest_run | run_id、source_id、开始/结束、发现/处理/重复/审核/拒绝/失败计数、预算使用、暂停原因 |
| moderation_audit | 对象/修订、操作者、动作、原因、前后状态、时间；不记录密码或完整请求头 |

现有用户和互动表尽量兼容。旧角色列与 role/user_role 表的实际使用需在迁移前核实；不得创建第二套不一致的授权事实源。

原文时间、采集时间、发布时间分别存储；内部统一 UTC，API 使用带时区的 ISO 8601，UI 按展示时区格式化。tags 通过 API 使用数组，不再让客户端处理 JSON 字符串。

历史文章迁移规则：先备份与盘点；不能仅按旧数字 ID 推断游戏；无法确认游戏、来源、发布状态的记录进入管理员检查清单；不自动删除，也不将历史草稿自动发布。

## 5. 采集管线与调度

### 5.1 处理阶段

```text
容量/任务互斥检查 → 获取来源配置 → 发现候选 URL
  → 规范化 URL + 元数据初筛 + 已成功交付检查
  → 有界正文请求/抽取 → 白名单游戏与内容类型判定
  → ACCEPT / REVIEW / REJECT
  → 必要时生成中文标题/摘要 → 输出结构校验
  → 持久 outbox → 内部 API → MySQL 事务提交 → receipt → 标记完成
```

优先采用官方结构化接口/RSS，其次单游戏栏目，再次综合媒体补充。网页里的“忽略规则”等文字只是被分析的数据，不是执行指令。抽取、分类和摘要分开：不要求模型同时重写完整 HTML、挑图、分类、摘要和决定数据库分类 ID。

适配器统一输出 RawArticle：sourceCode、originalUrl、title、language、originalPublishedAt（可空）、正文/文本、候选图片、抓取时间。来源特有选择器不进入全局业务逻辑。Trafilatura 仅作为待评测的抽取候选，不在没有样本对比时替换所有适配器。

### 5.2 默认运行预算

| 类型 | 检查频率 | 每次每来源候选上限 |
|---|---|---:|
| 官方公告/版本更新 | 6 小时 | 20 |
| 媒体资讯/电竞 | 12 小时 | 15 |
| 攻略/专题 | 24 小时 | 10 |

- 首期 6–8 个已验证来源；达不到质量要求时宁缺毋滥，不能为了凑数量启用未验证来源。
- 全项目一个采集任务、一个详情处理、一个 LLM 请求并发；来源间错峰。首期不安装常驻 headless browser。
- 每日最多 80 个新候选进入正文处理/AI 阶段，按 UTC 自然日记账。拒绝和失败也占用预算，不能只数发布成功的文章。
- 单候选同一网络阶段最多初次 + 2 次重试；AI 调用最多初次 + 2 次，日调用总上限 240 次；不得让外层重试和 SDK 内层重试相乘。
- 暂定请求超时：来源连接 5 秒、单请求总计 30 秒；AI 总计 60 秒；退避带抖动并遵守 Retry-After。最终数值由样本验证调整。
- 单轮任务默认最多 30 分钟；停止前保存进度。每天调度重启不能补跑大量历史轮次，合并过期轮次为一次有限任务。
- 已处理链接在抓详情前去重。未完成候选与分页游标持久保存；达到上限不得把整页永久标为完成。保留时间窗口与断点重扫防止当天多次更新漏采。
- Redis 故障不影响 outbox 安全；内部 API 或容量状态无法确认时停止新增处理，不无限生成待交付数据。
- dry-run 使用内存或独立临时状态，不写生产去重、预算、outbox、数据库，不调用付费 AI；另设显式评测命令，不能假借 dry-run 产生收费或发布副作用。

默认获取文本响应大小上限 2 MB（解压后），限制重定向次数和解析时间；分类输入有长度/token 上限。具体 token 限额和模型价格在真实模型确认后写入配置，不猜测模型可用性。

### 5.3 质量评测与发布开关

建立版本化的小型标注集：至少 160 条，四个游戏各至少 20 条明确相关正例，另外至少 80 条包含歧义词、广告、混合游戏、硬件、主播八卦、泛游戏等负例或审核边界样本。覆盖中英文及首期来源；只保存必要的可用测试摘录，避免在 Git 中打包整站网页。

规则调试样本与冻结评测样本分开。每次 prompt、模型、别名、抽取器或规则升级记录版本并重跑，不用同一批调参样本冒充独立验证。

初始上线门槛（工程验收目标，不是统计保证）：冻结集自动通过 precision ≥95%；明确正例的 ACCEPT+REVIEW 覆盖率 ≥90%；明确禁入负例不能自动发布。报告分母、样本数、逐类结果、审核率和误判原因，不能只报百分比。样本太少无法评估的来源先 REVIEW。

接入真实来源后先影子运行：自动决策但不自动发布，人工核查首批结果；通过后按来源单独开启自动发布。低量来源不能因等不到很多样本而伪造通过证据。

## 6. 可靠交付、去重与状态机

### 6.1 Python 持久 outbox

默认用采集器自带 SQLite 文件保存任务/结果 outbox，不新增数据库服务，也不承担线上文章查询。放在本项目专属持久卷，包含数据库、WAL、临时文件的容量都计入采集预算。

- 阶段：DISCOVERED → FETCHED → CLASSIFIED → READY_TO_DELIVER → ACKED；失败走 RETRY_WAIT 或 FAILED；业务判定 ACCEPT/REVIEW/REJECT 与传输阶段分开。
- 在开始处理一个候选前持久化任务 ID/eventId；处理完结果先原子提交 outbox，再发送 HTTP。进程重启恢复同一个 eventId，不重新随机生成。
- 已知输出结果重试交付不重复调用 AI。崩溃发生在输出落盘前，允许有限重算，但不能宣称网络外部调用 exactly-once。
- 本地保留结果直到收到后端已提交的 receipt。请求超时不等于失败，也不等于成功；使用同 eventId 重试。
- outbox 及运行状态软上限 50 MB、单交付载荷 ≤256 KB；临近容量停止新增，不删除未 ACK 的结果。大小限制失败进入人工可见状态，不截断后伪装成功。
- 任务锁覆盖整个采集运行；单实例之外再设置 OS/文件级互斥，防止手动运行与调度器同时处理。容器副本首期固定 1。
- 迁移旧 Redis 队列之前先盘点备份；停止旧两个消费者后受控转换，不清空队列或重复消费。

### 6.2 Java 事务幂等

内部入口：`POST /internal/v1/ingest/events`。只有独立采集服务身份可用，不通过 Web 公网代理暴露。普通用户 token、管理员 token 均不自动获得采集服务权限。

处理顺序：身份和载荷校验 → eventId/payloadHash 校验 → 事务插入 receipt/处理记录/文章或候选修订 → 按规则与容量决定发布或审核 → 提交事务 → 返回 receipt。

- eventId 唯一索引是并发下的最终防线，不依赖先查后插。
- 同 eventId、同 payloadHash 返回原结果；同 eventId、不同载荷返回 409，禁止覆盖。
- 同规范化 URL 的重复文章返回已有引用；内容更新形成候选修订。不同来源近重复先 REVIEW，首期不引入向量数据库。
- 来源、游戏、URL、状态、尺寸、摘要和内部规则版本再次服务端校验。不能因为 Python 发 ACCEPT 就无条件发布。
- 事务提交后响应丢失：重试取得已有 receipt；提交前异常：回滚后重试。文章和 receipt 不能分两次非事务写入。
- 验证错误/不兼容 schema 等 4xx 不无限重试；401/403 停止采集并告警；429/503 按预算退避；坏事件隔离并可人工重放。
- 采用 at-least-once 交付 + 幂等业务副作用，不宣称端到端 exactly-once。

重放期限首期 30 天；已完成 receipt 不早于该期限清理，超期事件返回明确错误，不当新事件重新发布。文章规范 URL/内容指纹不因 receipt 清理而丢失。未解决事件、未 ACK outbox 不按普通过期记录删除。

## 7. 前后端契约与页面整改

### 7.1 契约规则

## 8. 安全、审核与内容展示

- 文章写入、审核、来源配置和运维接口必须后端授权；前端守卫只是体验，不是安全边界。
- 内部采集凭据独立、可轮换，仅允许必要接口；密钥由部署配置注入，不放镜像、源码、网页构建产物或日志。
- 管理员身份不能由注册/更新资料载荷设置；验证现有 JWT 角色来源和更新生效方式。系统采集身份不再硬编码用户 1。
- HTML 服务端允许名单清洗；摘要按文本渲染；禁止模型产出的任意 HTML 直接进入 v-html。
- 采集只允许已配置 HTTP(S) 来源域名；限制重定向目标，拒绝 loopback、私网、链路本地及元数据地址，处理 DNS 重绑定风险。不得采集用户任意 URL 或执行网页指令。
- 原文跳转验证协议，外链启用安全属性。图片没有可用许可/来源条件时使用自有占位素材，不强制 OSS 搬运。
- 来源接入验证访问规则、限流及内容使用条件；不绕登录、付费墙或反爬访问控制。站内全文的来源授权/使用条件是后续门槛，摘要跳转不代表任何内容都可随意使用。
- 公开注册/登录/评论/统计接口设合理限流和载荷上限；未发布文章的互动也拒绝，避免绕过可见性边界。
- 评论需要删除/举报处置能力和最小运营流程；不具备时首期关闭评论提交，不以“功能已写”作为上线理由。
- 推送 demo、mock metrics 和批量模拟入口在生产禁用；不能以 obscurity 或改端口代替授权。

## 9. 隔离部署与版本管理

### 9.1 已获得的服务器快照

2026-09-20 15:08 左右（北京时间）只读检查：16 vCPU/KVM；内存约 15 GiB、available 约 11 GiB；根盘约 30 GB、已用 8.5 GB、可用约 22 GB；无 swap；已有多个业务服务，8080/8000/8443 等端口占用；现有 Redis 6.0.16、Java 21、Python 3.10.4；未发现常规 MySQL/Docker/Nginx 安装。

这是一个时刻的观测，不是独占资源、长期性能或端口永远空闲的保证。公网 NAT、80/443 可用性、带宽、供应商配额/备份能力尚未验证。

### 9.2 Compose 布局

固定项目名，例如 `gameboi`，所有容器、网络和卷有同一项目归属标签。首期五个服务：web、api、mysql、redis、ingest。

- web 是唯一业务发布端口；api/mysql/redis 无宿主机公开端口，ingest 无监听公网端口。
- db 内部网络只给必要服务加入；ingest 可访问来源和 AI 服务，但不拥有业务数据库凭据；不给应用 Docker socket 或 privileged 权限。
- 为每个组件创建独立账号、目录、凭据和数据卷；不挂载现有其他项目目录，也不复用宿主 Java/Python/Redis。
- 采用持久卷保存 MySQL、Redis 和 outbox；应用根文件系统尽可能只读，可写临时目录大小受限。
- 独立部署账号、SSH 密钥、最小权限。Docker 管理权限视为高权限管理能力，不默认授予应用用户。
- 安装 Docker 可能改变网络/防火墙；必须先记录原有监听/路由/服务健康，形成回退方案并取得批准。部署后逐一复核原有服务，不只检查本项目。
- 不运行全局 `docker system prune`；不执行清理所有容器/镜像/卷的命令；停本项目也不得附带删除持久卷。

### 9.3 版本选择与构建

现有依赖作为起点，先编译测试再冻结，不凭“最新”批量升级：Java 首先验证项目声明的 JDK 17；Python 候选 3.11；MySQL 候选 8.4 LTS；Redis 候选 7 系列；实际小版本、安全维护状态和镜像 digest 在部署任务中核实确认。Node 构建版本依据当前 Vite/插件的实际 engines 决定，旧文档“Node 18+”不作为安装依据。

- 每个镜像固定完整版本和 digest；不得用 latest。记录基础镜像、锁文件和构建环境。
- Maven wrapper/依赖、npm lockfile、Python 锁文件参与重现构建；Python 当前 >= 依赖范围需要冻结。
- 本地/CI 构建后发布镜像；生产服务器不执行 npm dev、Maven 编译、pip 在线安装一堆构建依赖。
- 非 x86_64 构建机需明确 Linux amd64 目标；本地 Windows 不通过 WSL/Bash 执行项目命令，使用 PowerShell 和获准的构建环境。
- 发布记录代码提交、镜像 digest、数据库迁移版本、规则/prompt 版本、配置校验和，不记录密钥值。

### 10.2 计量与验收

同时记录容器 cgroup 计量、内存限额、OOM/重启次数及宿主 available；不能只看 Java heap 或 Docker UI 的“去缓存”数字。项目容器内存和独立管理进程算项目占用；新安装容器运行时的增量开销也需要观测，不把它算成零。

默认 3.15 GB 容器预算提供余量，但**不是已经证明整体 ≤4 GB**。M6 以运行样本验证：正常、并发访问、采集同时进行、数据库备份/Redis 持久化峰值均不超过预算，无 OOM。若无法满足，先减连接/批量/缓存或串行安排重任务，不擅自提升上限。

若需要严格统一 cgroup 上限，在环境验证后将本项目容器归入独立父级 slice/cgroup；不能顺带限制或迁移其他应用。容器限额与宿主 Docker daemon 管理开销分别记账，不能宣称父级必然涵盖全部开销。

### 11.1 统计范围与预算

| 总预算 | 10.0 |

预算不是预分配，更不是每项都用满后还可继续增长。10 GB 是包含峰值开销的约束，不只是正常运行文件大小。

计量：专属数据卷/挂载、运行可写层、容器日志、归属本项目的镜像层、临时文件和项目备份全部计入；共享镜像层不能漏算，保守归属但避免同项目重复加算。记录实际分配字节与逻辑尺寸用于解释稀疏文件。镜像拉取、解压、双版本同时存在及迁移重建表也要预估峰值。

项目总量监控只读获取：宿主最小脚本写容量状态文件供项目读取；不把 Docker socket 交给 API。指标必须带采样时间，陈旧/不可用时采集 fail-closed。宿主脚本及定时器同样属于待批准部署操作。

### 11.2 容量状态机

| 状态 | 条件/行为 |
|---|---|
| NORMAL | <7 GB，预算与来源规则内运行 |
| WARNING | ≥7 GB，发一次有去重的预警，报告增长类别；仅清理已到期且允许清理的材料 |
| PAUSED_CAPACITY | ≥8 GB，停止新候选处理、AI 调用、媒体下载及所有自动发布；管理员发布也不能绕过空间检查 |
| EMERGENCY_READ_ONLY | 接近 9 GB、宿主剩余空间过低或增长异常时，禁止非必要业务写入，保留只读访问和告警；不能等到 10 GB 才处理 |
| UNKNOWN | 容量观测失效，暂停新增采集/自动发布，等待排查，不无限缓存工作 |

额外触发条件：宿主剩余可用空间低于 5 GB 时也暂停，哪怕本项目还没到 8 GB，避免其他应用增长拖垮磁盘。其他项目占用不算入本项目 10 GB，但必须影响写入安全判断。

- 每 60 秒监测，且每个采集批次、AI 调用前、发布和镜像拉取前做准入检查。仅定时检查不能构成严格磁盘上限。
- 暂停后已持久化 outbox 保留。已在途事件只有在预留空间允许时提交为待审核/暂停状态，不自动发布；空间不足返回明确可重试状态，由 outbox 保管，不能 ACK 后丢失。
- 业务写入（评论、浏览明细等）也计入增长预算，不能只暂停爬虫却允许数据库无限增长。紧急状态给客户端明确可重试错误，不假装写入成功。
- 为上线准备目录/卷可用的配额或等效存储限额方案，连同镜像/log 的可控保留一起验证。**如果没有可靠限额和峰值准入，仅靠“8 GB 时暂停”不能宣称严格保证 ≤10 GB**；这是 M6 发布门槛，不能未经评估直接改宿主文件系统挂载。
- 恢复需要管理员确认，并重新检查容量（建议 <7 GB）、依赖和故障原因；不因一次读数回落自动重启大量积压任务。
- 不自动删除已发布/用户/待审核业务内容；不为满足预算擅自提高 10 GB 或清理其他项目。

### 11.3 保留与备份

- 正常处理完成原始 HTML 默认 3 天；已解决失败样本默认 14 天；两者同时受 300 MB 总预算限制，必要时提前清理已解决样本。
- 未 ACK 结果、未解决审核证据不得套用上述 TTL 删除；积压占满预算就停采并提示管理员。
- 日志按大小和文件数量轮转并脱敏；详细成功记录短留、错误摘要长留但有总上限。已结束运行明细默认 30 天，长期仅保留有界聚合统计。
- binlog 保留取决于备份恢复目标，必须记录具体配置和使用量；max_binlog_size 只是单文件设置，不是所有日志总容量限制。
- 正常情况下每日异地备份，备份加密；初始工程目标 RPO ≤24 小时、RTO ≤4 小时，需实测恢复演练，不承诺尚未验证的 SLA。
- 备份尽量流式输出到独立存储，避免服务器生成全量临时备份。备份目标、账号、费用和告警渠道尚待用户确认，不能复用其他项目的 bucket/凭据。
- 未来正文增长接近预算时由用户决定归档/迁移/扩容；模型预留全文不代表无限永久存储。

## 12. 数据迁移与上线策略

1. 先固定旧版可重现基线，测试 P0 权限和可见性；不先搬目录。
2. 建版本化 schema：从空库完整初始化；旧库先只读盘点、备份、产生迁移计划。历史 sql/schema.sql 不是可直接反复运行的基线。
3. 渐进增加 nullable 字段与新表，回填分类/来源映射，生成无法确定记录清单；验证行数、关联、唯一约束，不默认重置数据库。
4. 后端先支持新 DTO 与迁移期兼容读，前端再切换；旧接口同样落实安全约束。
5. 旧 List 消费者和手动消费接口停用之前，确认旧队列数量/备份和新消费者切换方案。正式环境只有一条有效采集交付路径。
6. 单游戏纵向链路先在本地隔离环境通过（工程默认优先 CS2，因已找到源码参考，仍需来源实测），再扩展四游戏。
7. 四游戏来源影子运行 + 质量评测通过后逐来源开启自动发布；容量保护先于开启自动化。
8. 生产部署前检查审批、端口、NAT/HTTPS、宿主网络影响、备份、版本锁定和回退镜像空间；部署后回归其他既有服务。

回滚优先使用兼容旧版本的增量迁移；不可逆变更单独批准。回滚应用不自动回滚已经发布/审核的数据，不自动 down -v。需要恢复数据库时使用已验证备份流程，并报告影响时间段。

## 13. 验收与运营指标

### 13.1 必须通过的功能与故障场景

- 匿名/普通用户不能发布、编辑、审核、操作来源；不能经旧接口、push demo、内部采集入口绕过。
- 未发布文章在全部公开读取和互动接口不可见；管理员能审核系统采集文章。
- 四游戏/六类型可筛选；摘要、原文时间/语言/来源跨 Python→Java→MySQL→Vue 无丢失；空时间不伪造。
- dry-run 不改变生产状态；同 eventId 重发 10 次只产生一次业务效果；同 eventId 不同载荷返回冲突。
- API 提交后连接中断、采集进程中断、Redis 故障、数据库短暂不可用、AI 超时/畸形 JSON 均有可恢复或可人工处理结果，不无限重试、不默默丢弃。
- 7/8 GB 阈值、观测 UNKNOWN、outbox 满额、恢复检查可通过模拟指标测试；不通过真实写满宿主磁盘验证。
- 从空库迁移、旧库副本升级、镜像回滚、异地备份恢复均有证据。

### 13.2 初始性能验收负载（不是业务预测）

隔离测试环境 20 个并发读用户、5 个读请求/秒运行 30 分钟，列表与详情混合，同时执行一轮串行采集。目标成功率 ≥99%、读接口 p95 ≤1 秒（不含第三方原站/AI 耗时），无 OOM/无限增长；登录和评论等写入另做限流与正确性测试。

在生产真实主机做任何负载测试需另行批准并设置停止条件，不能影响现有服务。至少一轮真实 24 小时低频运行观察任务互斥、缓存、日志和 outbox 趋势；备份/持久化峰值另测。达不到目标时记录瓶颈并调整方案，不修改测试统计口径来“通过”。

### 13.3 轻量观测

首期使用结构化日志、数据库运行摘要、管理页和受限健康接口，不额外部署大型监控栈。记录：发现/成功/拒绝/审核/重复/失败数、来源成功率、事件积压与最老年龄、AI 请求/耗时/实际计费使用量（可取到时）、资源峰值和磁盘增长速度。

内存、容量、来源连续失败、认证失败、备份失败通知需要确定渠道。默认只在有意义的状态变化时通知，不每次采集刷屏。此设计不等于已经创建任何 Codex 自动化或服务器定时器。
